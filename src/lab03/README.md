# Лабораторная работа №3 - Наследование и иерархия классов

## Классы

### Базовый класс Server
Родительский класс для всех типов серверов. Хранит общие поля: hostname, ip_address, max_connections, status, current_connections.

### Производные классы

| Класс | Описание | Новые атрибуты | Новые методы |
|-------|----------|----------------|--------------|
| WebServer | Веб-сервер | domain, ssl_enabled | handle_request(), get_http_status() |
| DatabaseServer | Сервер БД | db_type, storage_gb | execute_query(), get_free_space() |
| FileServer | Файловый сервер | protocol, files | upload_file(), get_avg_file_size() |

### Полиморфные методы
- `get_server_type()` — возвращает тип сервера
- `calculate_load()` — вычисляет нагрузку (переопределён в каждом подклассе)

## Коллекция ServerCollection (из ЛР-2)

### Реализованные методы

| Метод | Описание |
|-------|----------|

## Сценарии использования

### Сценарий 1: Базовое наследование

**Что демонстрирует:** создание экземпляров разных типов (`WebServer`, `DatabaseServer`, `FileServer`), вызов методов дочерних классов, переопределение `__str__`.

**Как работает:** Инициализируются объекты `WebServer`, `DatabaseServer` и `FileServer`. У веб-сервера дважды вызывается `handle_request()`, затем выводится HTTP-статус. На сервере БД через `execute_query()` выполняются SQL-запросы, отображается объём свободного места. Для файлового сервера загружаются файлы через `upload_file()` и вычисляется средний размер. В завершение все объекты печатаются через переопределённый `__str__`, отражающий домен, тип БД, протокол и текущую нагрузку.

### Сценарий 2: Полиморфизм

**Что демонстрирует:** полиморфное поведение (один интерфейс — разная реализация), проверку принадлежности к типу через `isinstance()`, совместимость с коллекцией из ЛР-2.

**Как работает:** Создаётся `ServerCollection`, куда помещаются три сервера разных типов. Полиморфизм иллюстрируется через `get_server_type()`: каждый объект возвращает собственный тип. Метод `calculate_load()` показывает различную логику расчёта нагрузки в зависимости от класса. Через `isinstance()` определяются типы объектов и выводятся их уникальные атрибуты (SSL, тип БД, протокол). Коллекция корректно хранит и обрабатывает все варианты серверов.

### Сценарий 3: Фильтрация по типу и полиморфизм без условий

**Что демонстрирует:** выборку объектов по типу, полиморфизм без ветвлений (Good-паттерн), сводную статистику по категориям серверов.

**Как работает:** Формируется коллекция из 7 серверов разных классов (2 веб-сервера, 2 сервера БД, 2 файловых сервера и 1 базовый). Показывается фильтрация через `isinstance()`: отдельно выбираются веб-серверы, серверы БД и файловые серверы. Сравниваются анти-паттерн (`if type(server) == WebServer`) и Good-паттерн (`server.get_server_type()`). В конце выводится распределение серверов по типам.

## Вывод

В ходе работы были изучены следующие концепции:

- **Наследование** — построение дочерних классов `WebServer`, `DatabaseServer`, `FileServer` на основе `Server`
- **super()** — обращение к конструктору родительского класса
- **Переопределение методов** — изменение логики `__str__` и `calculate_load()` в подклассах
- **Полиморфизм** — единый метод `get_server_type()` с разным поведением в каждом классе
- **isinstance()** — определение типа объекта для фильтрации
- **Интеграция с коллекцией** — `ServerCollection` из ЛР-2 без изменений работает со всеми дочерними классами
- **Полиморфизм без условий** — применение общего интерфейса вместо явных проверок типа (Good-паттерн)
